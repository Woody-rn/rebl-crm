# Модель данных и бизнес-процессы ReblCRM

Документ описывает назначение таблиц базы данных (`001`–`014`) и то, как они взаимодействуют в сквозных бизнес-процессах CRM.

---

## 1. Схема сущностей по функциональным блокам

### Блок 1. Ядро и управление доступом (глобальные таблицы без RLS)

| Таблица | Назначение | Ключевые поля и особенности |
| :--- | :--- | :--- |
| **`tenants`** | Реестр компаний-клиентов (рабочих пространств) SaaS-платформы. | `slug` (уникальный адрес для публичной записи `/public/{slug}`), `timezone` (по умолчанию `UTC`), `status` (`ACTIVE`, `TRIAL`, `SUSPENDED`). |
| **`users`** | Сотрудники внутри компании (владельцы, администраторы, менеджеры). | Привязаны к `tenant_id`. Хранят `email` (частичный уникальный индекс для активных пользователей `WHERE deleted_at IS NULL`), `password_hash`, `role`, `telegram_user_id` для уведомлений бота. |

### Блок 2. Клиентская база (изолированы через PostgreSQL RLS)

| Таблица | Назначение | Ключевые поля и особенности |
| :--- | :--- | :--- |
| **`contacts`** | Физические лица (клиенты, ученики, лиды). | `first_name`, `last_name`, `phone`, `email`, `telegram_chat_id`, `telegram_username`, `owner_id` (ответственный менеджер), `company_id` (опционально, для B2B), `custom_data` (`JSONB` с GIN-индексом). |
| **`companies`** | Организации (юридические лица в B2B-сегменте). | `name`, `inn` (частичный составной индекс), `kpp`, `industry`, `website`, `address`, `custom_data` (`JSONB`). К одной компании может быть привязано множество контактов. |

### Блок 3. Воронки продаж и сделки (изолированы через PostgreSQL RLS)

| Таблица | Назначение | Ключевые поля и особенности |
| :--- | :--- | :--- |
| **`pipelines`** | Воронки продаж (направления бизнеса одного тенанта). | `name` (например, «Основная продажа», «Продление»), `is_default`, `sort_order`. |
| **`stages`** | Этапы (колонки) канбан-доски внутри конкретной воронки. | `pipeline_id`, `name`, `color`, `sort_order`, `win_probability` (0–100%), `is_final` и `final_type` (`WON` / `LOST`). |
| **`deals`** | Сделки (карточки на канбан-доске). | Связывает клиента (`contact_id`), компанию (`company_id`), этап (`stage_id`) и менеджера (`owner_id`). Хранит `amount`, `currency`, `expected_close_date`, `lost_reason`, `custom_data`. |

### Блок 4. Операционная работа и история (изолированы через PostgreSQL RLS)

| Таблица | Назначение | Ключевые поля и особенности |
| :--- | :--- | :--- |
| **`tasks`** | Задачи и напоминания для сотрудников. | `title`, `status` (`PENDING`, `IN_PROGRESS`, `DONE`, `CANCELED`), `priority`, `assignee_id`, `due_date`. Полиморфная привязка через `entity_type` + `entity_id` (`DEAL`, `CONTACT`, `COMPANY`). |
| **`activities`** | Единая хронологическая лента событий и взаимодействий. | Фиксирует всё, что происходило с сущностью: `CALL`, `EMAIL`, `MEETING`, `TELEGRAM_MESSAGE`, `NOTE`, `DEAL_STAGE_CHANGE`. Хранит `occurred_at` и `metadata` (`JSONB`). |
| **`attachments`** | Метаданные файлов, загруженных в S3-хранилище MinIO. | `file_name`, `mime_type`, `file_size`, `storage_key`, `uploaded_by_id` и полиморфная привязка к сущности (`entity_type` + `entity_id`). |

### Блок 5. Гибкость и асинхронная инфраструктура

| Таблица | RLS | Назначение |
| :--- | :---: | :--- |
| **`custom_field_definitions`** | Да | Справочник кастомных полей, которые бизнес настраивает сам под свою нишу (`TEXT`, `NUMBER`, `SELECT`, `DATE` и др.) без миграций БД. |
| **`outbox_events`** | **Нет** | Системная очередь паттерна **Transactional Outbox**. В одной транзакции с бизнес-операцией сюда пишутся события (`DEAL_WON`, `BOOKING_CONFIRMED`), которые фоновый воркер гарантированно отправляет в Telegram и внешние сервисы. |

## 2. Сквозные бизнес-процессы

### Процесс 1: Онбординг новой компании (Регистрация)
1. Создаётся запись в **`tenants`** с уникальным `slug` и часовым поясом.
2. Создаётся первый пользователь в **`users`** с ролью `OWNER`, привязанный к новому `tenant_id`.
3. Инициализируются стартовая воронка в **`pipelines`** и базовые этапы в **`stages`** (например: *Новый лид → В работе → Успешно / Отказ*).
4. При выборе вертикального шаблона (репетитор, салон, агентство) заполняются метаданные в **`custom_field_definitions`**.

### Процесс 2: Входящее обращение через Telegram или AI-парсинг
1. Клиент пишет в Telegram-бота (или менеджер наговаривает голосовое сообщение AI-ассистенту).
2. Система ищет контакт в **`contacts`** по составному индексу `(tenant_id, telegram_chat_id)` или `(tenant_id, phone)`. Если контакт не найден — создаётся новый.
3. Текст сообщения или расшифровка голоса сохраняется в ленту **`activities`** (тип `TELEGRAM_MESSAGE` или `NOTE`). При наличии вложений файлы загружаются в MinIO, а ссылки фиксируются в **`attachments`**.
4. При необходимости автоматически создаётся карточка сделки в **`deals`** на первом этапе воронки и задача на перезвон в **`tasks`**.

### Процесс 3: Ведение сделки по воронке и уведомления
1. Менеджер перемещает карточку в **`deals`** на следующий этап (`stage_id`).
2. В рамках **одной транзакции** PostgreSQL:
   - Обновляется `stage_id` (и `closed_at`, если этап финальный) в **`deals`**;
   - Добавляется системная запись `DEAL_STAGE_CHANGE` в **`activities`**;
   - Создаётся событие (например, `DEAL_WON`) со статусом `PENDING` в **`outbox_events`**.
3. Фоновый воркер (`@Scheduled`) забирает запись из **`outbox_events`** и отправляет уведомление клиенту или руководителю в Telegram с автоматическими повторами при сбоях сети.
